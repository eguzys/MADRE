## How to build

```bash
cd <repo>/omnet_smoke

# (First time only — regenerate Makefile if you move the directory)
INET=<path to inet4.6>
opp_makemake -f --deep -o omnet_smoke \
    -KINET_PROJ=$INET \
    -DINET_IMPORT \
    -I$INET/src \
    -L$INET/src \
    -lINET \
    -lzmq

make MODE=release
```

## Implementation notes

### 1. `parseActionJson` is skipped on the `done=True` ack

**In `RLBridge.cc` `handleMessage()`:**

When `done=true`, Python sends `{"type":"ack"}` (no `"actions"` key) as a courtesy ack so
OMNeT++'s socket doesn't stall. Parsing that reply as an action would throw `cRuntimeError`
because `"actions"` is missing.

The parse is guarded behind `if (!done)`:
```cpp
if (!done) {
    parseActionJson(actionJson);
}
```

### 2. NED package must match directory structure

OMNeT++ enforces that a NED file's declared `package` matches its path relative to the NED
root directory. `package inet.mobility.single` works inside INET's source tree but not for
a standalone project.

The package is `rlsmoke`, with all NED files in an `rlsmoke/`
subdirectory so the path matches. The NED root is the project root (`omnet_smoke/`).

The `@class` annotations use `inet::RLBridge` and `inet::RLControlledMobility`
(explicit namespace) so OMNeT++ finds the registered C++ classes correctly.

### 3. `bridgeModule` path: `^.^.rlBridge` not `^.rlBridge`

The default `"^.rlBridge"` resolves correctly only when
`RLControlledMobility` is a **top-level** network submodule. In this project it sits one
level deeper, inside `DroneHost`:

```
SmokeNet.host[0].mobility   ← RLControlledMobility lives here
SmokeNet.rlBridge           ← bridge lives here
```

From `mobility`, `^` → `host[0]`, `^.rlBridge` → not found.  
With `^.^.rlBridge`: first `^` → `host[0]`, second `^` → `SmokeNet`, `.rlBridge` → found.

Set in `RLControlledMobility.ned`.

### 4. `ned-path` in `omnetpp.ini` can't use Makefile variables

OMNeT++'s ini parser does not expand `${INET_PROJ}` (a Makefile variable). A literal
`${INET_PROJ}` would cause a "cannot canonicalize" error at startup. The ini has no `ned-path`;
both paths are passed via `-n ".:$INET/src"` on the command line.

### 5. Constraint area must be finite for random initial placement

`MobilityBase::setInitialPosition()` places modules at a random position within the
constraint area. The default bounds are `(-inf, +inf)`, which yields `NaN` position —
OMNeT++ then aborts with "Mobility position is not a finite number after initialize".

**Set in `omnetpp.ini`:**
```ini
**.mobility.constraintAreaMinX = 0m
**.mobility.constraintAreaMinY = 0m
**.mobility.constraintAreaMinZ = 0m
**.mobility.constraintAreaMaxX = 1000m
**.mobility.constraintAreaMaxY = 1000m
**.mobility.constraintAreaMaxZ = 0m
```

## Network architecture

```
SmokeNet (rlsmoke.SmokeNet)
├── rlBridge : RLBridge           ZMQ REQ socket, blocks 1 Hz on Python
├── host[0]  : DroneHost
│   └── mobility : RLControlledMobility   droneId=0, reads velocity from rlBridge
└── host[1]  : DroneHost
    └── mobility : RLControlledMobility   droneId=1, reads velocity from rlBridge
```

`DroneHost` is a bare compound module (no radio/IP/app). Its only role is to provide an
extra level of hierarchy so `bridgeModule = "^.^.rlBridge"` resolves correctly, and so the
`subjectModule = "^"` default in `MobilityBase` points to `DroneHost` (a valid cModule).

## Timing behaviour

- `syncInterval = 1s`, `maxSteps = 5`: rlBridge fires at t=0,1,2,3,4,5.
- Steps 0–4 are `done=false`; Python sends random 2-element action arrays.
- Step 5 (`t=5s`) is `done=true`; Python sends `{"type":"ack"}` and exits.
- After step 5, the rlBridge stops rescheduling itself.
- `MovingMobilityBase`'s own `moveTimer` (every `updateInterval=0.5s`) keeps firing until
  `sim-time-limit=10s`. This is normal — positions keep integrating the last action.
- `finish()` attempts a best-effort `dontwait` send; Python has already closed its socket
  so this throws a ZMQ exception that is swallowed in the catch block.
